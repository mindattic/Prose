# /redeploy — rebuild every Prose app into the production folder

Republishes **Hub, Writer and Launcher** to `C:\Apps\MindAttic\Prose\` (each only if its source
changed since it was last deployed), then restarts the Hub so the session is talking to the build
you just made. KdpPublish is its own repo now and deploys to `C:\Apps\KdpPublish\` — not part of this.

Use it after changing any C# under `src/`. The SessionStart hook
(`.prose/hooks/start-prose-hub.ps1`) only ever redeploys **the Hub**, and only when source is newer
than the deployed exe — it deliberately never touches Writer, because republishing an exe the
author is looking at would stop it mid-edit. `/redeploy` is the explicit "refresh everything" step.

## Usage

```
/redeploy                      all three apps (only the ones whose source changed)
/redeploy Hub Writer           only the ones named
/redeploy force                clean rebuild of all of them, changed or not
```

Valid names: `Hub`, `Writer`, `Launcher`.

## What to run

From the repository root:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy.ps1
```

with `-Apps Hub,Writer` when the user named a subset, and `-Force` for a clean rebuild.

Without `-Force` an app is republished only when its deployed exe or `deploy.bat` is missing, or a
source file of that app (its project plus every project it references, transitively, and linked
files; bin/obj excluded) is newer than its deployed exe. Otherwise it prints "up to date, skipped"
and does not stop it.

The script publishes framework-dependent, win-x64, single-file, via `--artifacts-path` so the build
graph never writes into the repo's `bin/obj` — that is what lets it run while `Prose.Mcp.exe` holds
its own DLLs open for the length of the session. **Never kill `Prose.Mcp.exe` to get a build
through; that ends the user's session.**

## Steps

1. **Warn if the Writer is open.** `Get-Process Writer` — republishing stops it and the author
   loses whatever beat they had open. Ask before stopping it; don't just take it down.
2. **Publish.** Run the command above. For each app that needs it, it stops the target by
   *executable path* (not just process name — `Hub` and `Launcher` are generic enough to match
   something unrelated), polls up to 10s for the file lock to release, then publishes.
3. **Restart the Hub** if it was republished. The publish stops it and does not start it again:
   ```powershell
   $env:ASPNETCORE_ENVIRONMENT = 'Development'
   Start-Process 'C:\Apps\MindAttic\Prose\Hub.exe' -WorkingDirectory 'C:\Apps\MindAttic\Prose'
   ```
   `ASPNETCORE_ENVIRONMENT` matters: with nothing set, ASP.NET Core defaults to Production, which
   makes `AddMindAtticAuthentication` fail closed and silently drops `--reset-password`.
   (`deploy.ps1 -Apps Hub -Start Hub` does this and waits for `/api/health` itself.)
4. **Verify, don't assume.** A successful publish is not a working Hub:
   ```
   curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:5900/api/health    # 200
   curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:5900/app           # 200
   curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:5900/writer        # 200
   ```
   `/api/health` is fail-closed — it returns 503 when SQL Server is unreachable — so a 200 there
   means genuinely usable, not merely "a process is listening". Report the exe sizes and the three
   status codes.

## `C:\Apps\MindAttic\Prose\deploy.bat`

Generated by `deploy.ps1` on every run; the desktop shortcuts point at it. It redeploys from source
*before* starting (a fast no-op when nothing changed), so you can never be looking at a stale exe:

| Shortcut | Command | Redeploys | Starts |
|---|---|---|---|
| Prose Writer | `deploy.bat Writer` | Writer **only** | `Writer.exe`, which connects to the running Hub or starts the deployed one |
| Prose Hub | `deploy.bat Hub` | Hub **only** | `Hub.exe`, or connects to a Hub already healthy on 5900 |
| Deploy Prose | `deploy.bat` | all three | `Launcher.exe` |

If the repo is missing or the publish fails, it launches whatever is already in the folder instead.
If the Hub was started but never answered `/api/health` (deploy.ps1 exit 2), it reports DEPLOY
FAILED rather than starting a second Hub.

Each app deploys alone. A Writer deploy never stops or replaces the Hub, and a Hub deploy never
touches an open Writer: the Writer shows "Lost the connection" while the Hub is down and reopens the
editor by itself when the new Hub answers. It only polls — it never starts a Hub mid-deploy, which
would lock the Hub.exe being replaced.

**Which one a change needs.** The editor — every Razor component, the save path, the entity modal —
is `Prose.WriterUi`, compiled **into Hub.exe**. `Writer.exe` is only the window: WebView2, the splash,
Connect, the microphone permission. So a change under `Prose.WriterUi`, `Prose.Hub` or `Prose.Core`
needs **the Hub** deployed; a change under `Prose.Writer` needs the Writer. When starting the Writer
without the Hub, `deploy.ps1` says which Hub the Writer will use and warns when that Hub was built
before the latest change to what it serves.

## Gotchas

- **`-Apps` must tolerate however PowerShell mangles it.** `powershell -File script.ps1 -Apps
  Hub,Writer` passes the single *string* `"Hub,Writer"`, and `-Apps Hub Writer` binds only `Hub` and
  silently drops the rest. `deploy.bat` invokes the script through `-File`, so `deploy.ps1`
  splits and validates the value itself instead of using `[ValidateSet]` — which would have rejected
  the first spelling and quietly mis-deployed the second. Don't "simplify" that back to a ValidateSet.

- **The MCP server is not redeployed by this.** `Prose.Mcp.exe` is a separate long-lived process
  launched by the client, running from the repo's `bin\Release`. If its schema is stale, the fix is
  to exit Claude Code and start a new session — the SessionStart `build-prose-mcp` hook rebuilds it
  while it is not running. `/redeploy` cannot fix a stale MCP schema.
- The old `src\Prose.Hub\tools\deploy.ps1` still works — it forwards to `deploy.ps1 -Apps Hub`.
